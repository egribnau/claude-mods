# claude-mods

Personal Claude Code mods, distributed as a plugin marketplace.

## Install

```
/plugin install whats-next --marketplace egribnau/claude-mods
```

Answer `y` to add the marketplace, then pick a scope.

## Update an existing machine

```
/plugin marketplace update egribnau-mods
```

## Layout

```
.claude-plugin/marketplace.json      marketplace manifest
plugins/whats-next/                  a mod: a hooks module, no skills
  .claude-plugin/plugin.json         plugin manifest, settings under userConfig
  hooks/register.tsx                 the hooks module: the panes and /next
  hooks/tracker.ts                   what the panes ask a tracker
  hooks/forgejo.ts                   Forgejo as a tracker: every Forgejo URL
  hooks/gitlab.ts                    GitLab as a tracker: every GitLab URL
  hooks/github.ts                    GitHub as a tracker: every GitHub URL
  types/index.d.ts                   the session state it keeps
  tests/*.test.ts                    run with `claude plugin test plugins/whats-next`
```

## Mods

| Mod | What it does | Requires |
| --- | --- | --- |
| What's Next (`whats-next`) | `/next` opens a docked pane on the Forgejo, GitLab or GitHub repo behind the current directory's `origin`. Until setup is complete, the pane guides it step by step: the repo, the forge at its host, a token, and the token reading the repo. github.com and gitlab.com are known by name; any other host is asked, without a token, for its version as Forgejo or Gitea, then GitLab, then GitHub Enterprise. On GitHub (github.com or GitHub Enterprise), What's Next shows What's next and the detail of an issue, with its last comment, the pull requests of the repo that mention it and the commits that refer to it, from the issue's timeline; pull requests are left out of every list, and GitHub tracks no time. It assigns, unassigns, closes and reopens GitHub issues with push rights on the repo; a classic token also needs `repo` (`public_repo` will do on a public repo), and a fine-grained token, whose permissions GitHub does not list, needs Issues read and write, which setup's Actions step cannot check: the buttons show, and GitHub has the last word. Blockers on GitHub are its own "blocked by" relations, within the repo: an issue that waits on an open one is shown blocked, and the detail lists what blocks it and what it blocks. The list of open issues already says how many open issues block each one, so only the blocked ones cost a request. On GitHub an epic is an issue with the Epic label, open or closed, and its children are its sub-issues in the repo; a sub-issue says how many open issues block it, so only blocked ones are asked what blocks them. On GitLab, What's Next shows What's next and the detail of an issue, numbered by the project's own issue numbers, with its time spent and estimate, its last comment and the merge requests that mention it, and its epics. On GitLab an epic is an issue with the Epic label, and its children are the issues it links as related (another epic linked that way is left out). Blockers come from blocking links, which only GitLab EE has: there What's Next finds what blocks an issue as on Forgejo; on GitLab Free or Community Edition there are none, so nothing shows as blocked. It assigns, unassigns, closes and reopens GitLab issues with an `api` token and Reporter or higher on the project; with `read_api` only, or a lower role, setup's Actions step says read only and why. Then it shows what's next: In progress (open issues assigned to you), Next (the oldest open, unassigned issue with no open dependencies, or Nothing available when all are blocked), and the Queue (the next 10 unassigned issues after Next, oldest first, each checked for open dependencies as Next is; the ones found blocked go to the bottom, and the rest are counted in one line, "and 14 more"; past Next at most 20 issues are checked, so a load asks a bounded number of times). Each row's mark says how it stands for you (● yours, ⊘ blocked, ○ available); Next is also bold and the focus starts on it, so Enter opens it. A due date, an issue's or a milestone's, is red once passed, amber within 7 days and dim otherwise. A milestone picker, shared with Epics, narrows every section to one open milestone (at first the one due first), to the issues without one, or to All. At the bottom: how many open issues it shows and how many are yours, and at the right What's Next's own version from its manifest (the one the session loaded, until `/reload-plugins`), which keeps its place on a narrow pane. The Epics pane ends its bottom line in the version too, and the issue detail shows only the version there. Issues assigned to others are left out. Selecting an issue shows its detail (labels, due date, branch, tracked time, what blocks it and what it blocks, pull requests and commits that refer to it, its description and last comment; the heading grey as a whole once the issue is closed) with Work on this, which drafts a prompt from the issue (and assigns you first), Assign me or Unassign me, Close or Reopen, and Open in browser. Each issue under Blocked by and Blocks is a line to select: it opens that issue's detail in the same pane, Back (named for it, `← #29`) returns to the issue it was opened from, and from there to the list. An open blocker that is itself blocked says `blocked`, which costs a request per open blocker on Forgejo and GitLab (GitHub says so with the blocker); a closed one ends in a grey ✓. Issues in another repo are left out on every forge, since What's Next shows this repo's numbers only. Once one of these changes the issue (Open in browser aside), the pane goes back to the list the issue was opened from, What's next or Epics, which shows the change; a refused change keeps the issue open with why. Assigning and closing need a token with `write:issue` and push rights on the repo (on GitLab, `api` and Reporter or higher); setup's Actions step says whether What's Next may, and why not. After a change, What's next shows the issue as the change left it, read again from the forge, for 30 seconds, since a forge's lists may lag a change (GitHub's do, by a few seconds). When the repo has open epics, an Epics pane opens as a tab next to What's next (Refresh opens it once the first epic is there, and closes it when none is left): the epics of one open milestone, at first the one due first, each with a bar of its closed children (a picker switches to another milestone, to the epics without one, or to All, a group per milestone); folded, a line says what is yours, blocked or available, or all closed (amber: close it) once every child is, its ⊕ or ⊖ folds it open on its open children, as rows like What's next's (● yours, ⊘ blocked, ◌ with others, their name at the right, ○ available), and the rest of its row opens the epic's detail. The epics form a tree: a child with children of its own has a ⊕ or ⊖ in place of its mark, coloured by how it stands for you (green yours, dim blocked, plain otherwise, with others named at the right), with closed/total of its children at the right, and folds open on them two columns further in, as deep as the forge goes. On GitHub that is any sub-issue with sub-issues of its own, label or not, its count coming with it. On Forgejo an epic another epic depends on is no child of it but something it waits for, and on GitLab a related link does not say which issue is the parent, so there the tree is one level deep. An epic held by an open epic in the pick shows only under it, not also at the top; an issue shown a second time (under two parents, or in a loop) shows ↑ and shown above, and does not fold. Children are asked when their parent first folds open; what is folded open holds over Refresh and Back. When the repo has open milestones, a Milestones pane opens as a tab after Epics, the same way (`/next` opens it again after it was closed): every open milestone, the one due first at the top and those without a due date last, each with a bar of its closed issues and closed/total, and under it two lines: its due date, coloured as elsewhere, and how many of its issues are open, or all closed (amber) once every one is; then what is yours, blocked or available, as far as the pane already knows without asking (yours from the lists; blocked and available only once every issue in it that is not yours has been checked for blockers), or no second line when it knows nothing. It has no picker; its bottom line counts the milestones and their open issues. Its ⊕ or ⊖ folds a milestone open on its open issues, taken from the lists already loaded, as rows like an epic's children (● yours, ⊘ blocked, ◌ with others, their name at the right, ○ available), then how many are closed; each one not yours is checked for blockers once, as What's next checks its own, and the second line under the milestone then says all of what is yours, blocked or available. Its epics come first, each with a bar of its closed children and under it what is yours, blocked or available in it, as on the Epics pane; its ⊕ or ⊖ folds it open on its tree, as on Epics, and what is folded open is shared with Epics. An issue an open epic in the milestone holds shows only under that epic, not also in the list, and an epic held by another epic in it only under that one. An epic's own children never count as its blockers, and they are asked once for Milestones and Epics both. What is yours, blocked or available under the milestone leaves its epics out. A row opens the issue's detail, and Back returns to Milestones. The rest of a milestone's row, open or closed, opens its detail: the title, open or how long ago it closed (GitLab does not say when), its due date, the bar with closed/total and how many are open, or all closed (amber while the milestone is open), what is yours, blocked or available (its issues are asked when the detail opens, unless a fold already did, and the two share them), Open in browser for the milestone's page on the forge, Close or Reopen, then two sections that fold on their rule: Issues, its issues as the same tree as in the list, open at first, and Description, its first three lines and how many more until it is folded open (a description of three lines or fewer has nothing to fold); both folds hold for every milestone. Back returns to the list with its folds as they were. Close and Reopen act at once, as on an issue, open issues and all (they keep the milestone); the pane then goes back to the list, read again, where a closed milestone sits under Closed, and a refusal keeps the detail open with why. They need the same token rights as closing an issue; on GitLab a milestone of a parent group closes in that group, so the token must be allowed to change the group. A folded milestone asks the forge nothing; folds hold over Refresh, which checks again only the milestones folded open. Under the open milestones, a Closed rule, folded at first, holds the last three milestones closed, newest first (on GitLab, which does not say when a milestone closed, the last changed), each a grey row ending in ✓; folded open, a closed milestone shows its open epics and issues as above, its closed epics as grey rows ending in ✓, and how many of its issues are closed. An epic is an issue with the Epic label; its children are the issues it depends on (on GitLab, the issues it links as related; on GitHub, its sub-issues). The picker switches from what was loaded, and an issue opened again shows from memory; Refresh and `/next` ask the forge again. `/next epics` (or `e`) opens the panes with Epics in front; `/next next` (or `n`) does what `/next` does. When another plugin, a user command or an MCP server already has `/next`, the command is `/whats-next` in that session, and a toast says so. | a Forgejo, GitLab or GitHub access token; Forgejo, Gitea, GitLab or GitHub |

What's Next has eight settings. **Compact** (`ask`, `on` or `off`): lists without an empty line between rows; with `ask`, What's Next asks once, after Icons. **Epic label** (default `epic`): the label that makes an issue an epic; on GitLab its children are the issues it links as related, on GitHub its sub-issues. **Debug** (off by default): a line under the repo line counts What's Next's requests to the forge, for the last action and for the session. **Icons** (`ask`, `icons` or `text`, in `/config` under What's Next): buttons as Nerd Font
icons or as words; with `ask`, What's Next asks once, right after setup. **Forgejo tokens**: Forgejo or Gitea
access tokens, kept in secure storage. A bare token is for every host; more hosts take `host=token`
pairs separated by spaces (`git.example.org=<token> codeberg.org=<token>`), and a pair wins over a
bare token. `/config` does not list it: set it with `/plugin configure whats-next@egribnau-mods` (setup names the marketplace What's Next was installed from). A token needs `write:issue`,
`read:repository` and `read:user` (to know which issues are yours); with `read:issue` in place of
`write:issue`, What's Next is read only and cannot assign or close. **GitLab.com token**: a gitlab.com access token, kept in secure storage.
**Private GitLab token**: an access token for your own GitLab, any host but gitlab.com, kept in secure
storage; `host=token` pairs separated by spaces still work for more than one host. A `gitlab.com=<token>`
pair there still counts for gitlab.com when GitLab.com token is empty. A GitLab token needs `api` to
assign and close, or `read_api` to read only. **GitHub token**: a GitHub access token, kept in secure storage, for
github.com and GitHub Enterprise; `host=token` pairs separated by spaces for more than one host. A fine-grained
token needs the Issues permission (read and write to assign and close, read to read only), a classic one `repo`.
What's Next reads no environment variables and no other tool's files. A token goes only to the host it is
for, as the forge setup found there, and What's Next shows it nowhere: a forge's error that echoes it back
shows `<token>` in its place.

What's Next is for the terminal. A Code session in the Claude desktop app loads it but gets none of its
settings: the secret token settings stay empty there, so the pane stops at the Token step. The desktop app
also runs the copy `claude plugin update whats-next@egribnau-mods` made from the last commit, not the
working folder.

To edit What's Next and see each change without a push, add this working copy as a marketplace
(`claude plugin marketplace add ~/dev/personal/claude-mods`) and install from it; Claude Code then
reads the folder itself, and `/reload-plugins` picks up an edit.
