# claude-mods

Personal Claude Code mods, distributed as a plugin marketplace.

## Install

```
/plugin install whats-next --marketplace egribnau/claude-mods
```

Answer `y` to add the marketplace, then pick a scope.

## Update an existing machine

```
/plugin marketplace update egribnau-mods
```

## Layout

```
.claude-plugin/marketplace.json      marketplace manifest
plugins/whats-next/                  a mod: a hooks module, no skills
  .claude-plugin/plugin.json         plugin manifest, settings under userConfig
  hooks/register.tsx                 the hooks module: the panes and /next
  hooks/views/*.tsx                  each view of a pane: the lists, the details, help, setup
  hooks/draw.tsx                     how a row or a line is drawn, for every view
  hooks/tracker.ts                   what the panes ask a tracker
  hooks/setup.ts                     setup's steps and the tracker they end in: which token a host gets
  hooks/forgejo.ts                   Forgejo as a tracker: every Forgejo URL
  hooks/gitlab.ts                    GitLab as a tracker: every GitLab URL
  hooks/github.ts                    GitHub as a tracker: every GitHub URL
  types/index.d.ts                   the session state it keeps
  tests/*.test.ts                    run with `claude plugin test plugins/whats-next`
```

## Mods

| Mod | What it does | Requires |
| --- | --- | --- |
| What's Next (`whats-next`) | `/next` opens a docked pane on the Forgejo, GitLab or GitHub repo behind the current directory's `origin`. Until setup is complete, the pane guides it step by step: the repo, the forge at its host, a token, and the token reading the repo. github.com and gitlab.com are known by name; any other host is asked, without a token, for its version as Forgejo or Gitea, then GitLab, then GitHub Enterprise, once a session: Refresh keeps the answer. On GitHub (github.com or GitHub Enterprise), What's Next shows What's next and the detail of an issue, with its comments, the pull requests of the repo that mention it and the commits that refer to it, from the issue's timeline; pull requests are left out of every list, and GitHub tracks no time. It assigns, unassigns, closes and reopens GitHub issues with push rights on the repo; a classic token also needs `repo` (`public_repo` will do on a public repo), and a fine-grained token, whose permissions GitHub does not list, needs Issues read and write, which setup's Actions step cannot check: the buttons show, and GitHub has the last word. Blockers on GitHub are its own "blocked by" relations, within the repo: an issue that waits on an open one is shown blocked, and the detail lists what blocks it and what it blocks. The list of open issues already says how many open issues block each one, so only the blocked ones cost a request. On GitHub an epic is an issue with the Epic label, open or closed, and its children are its sub-issues in the repo; a sub-issue says how many open issues block it, so only blocked ones are asked what blocks them. On GitLab, What's Next shows What's next and the detail of an issue, numbered by the project's own issue numbers, with its time spent and estimate, its comments and the merge requests that mention it (`!61`, as GitLab numbers them), and its epics. On GitLab an epic is an issue with the Epic label, and its children are the issues it links as related (another epic linked that way is left out). Blockers come from blocking links, which only GitLab EE has: there What's Next finds what blocks an issue as on Forgejo; on GitLab Free or Community Edition there are none, so nothing shows as blocked. It assigns, unassigns, closes and reopens GitLab issues with an `api` token and Reporter or higher on the project (GitLab Free keeps one assignee, so Assign Me there makes the issue yours alone); with `read_api` only, or a lower role, setup's Actions step says read only and why. Then it shows what's next: In progress (open issues assigned to you), Next (the first unassigned issue with no open dependencies, or Nothing available when all are blocked), and the Queue (the next 10 unassigned issues after Next, each checked for open dependencies as Next is; the ones found blocked go to the bottom, and the rest are counted in one line, "and 14 more"; past Next at most 20 issues are checked, so a load asks a bounded number of times). Next follows on from where you work: the epic of your issue in progress (the one updated last), or else of the issue you closed last, from anywhere (the pane, the browser, a commit). Its open issues come first, then those of the epic above it (on GitHub, where sub-issues nest), then the rest of that issue's milestone, then the rest. Within each, an issue due within 7 days or past due comes first (an issue without a due date takes its milestone's), then the one most issues wait on, then the oldest. The rules say where each part comes from, `Next · in epic #30`, `Queue · in epic #30`, and the Queue's rules have no count. Above the bottom line, `Last closed · 2h ago · in epic #30` and the issue you closed last, grey, which opens it. Finding where you work costs three requests the first time the milestone filter is set to a milestone (your last closed issue in it, its epic, the epic's children, unless Epics loaded them), and one more when you have an issue in progress (the epic of your last closed one); then nothing until Refresh. Each row's mark says how it stands for you (● yours, ⊘ blocked, ○ available); Next is also bold; nothing has the focus until Tab or an arrow key moves it. The line under a row says, in this order, how many open issues block it (⊘ 2), how many open issues wait on it (↦ 2), both counted, which ones in the issue detail, its own due date (⧗ 14 Oct; GitHub issues have none), its milestone, its labels in their colours, and how long ago it was opened (✎ 3d). A due date, an issue's or a milestone's, follows ⧗ and is red once passed, amber within 7 days and dim otherwise; where there is none, nothing is shown. A milestone filter, shared with Epics, narrows every section to one open milestone, to the issues without one, or to All. `/next` starts it where you work: the milestone of your issue in progress, else of the issue you closed last, else the one due first; one you choose holds until the next `/next`. Every pane and detail ends, after an empty line, in one line, `── What's Next · v0.74.2`: What's Next's own version from its manifest (the one the session loaded, until `/reload-plugins`); it counts nothing, and pressing it opens What's Next's repository in the browser. On a narrow pane it is cut at its end. Issues assigned to others are left out. Selecting an issue shows its detail: the title with the issue's mark before its number, as in the lists (a grey ✓, the title grey as a whole, once the issue is closed), under it who opened it when (`✎ 3w jdoe`), then its facts, each under its name: the epic it is a child of (Parent on GitHub when that is no epic; on Forgejo and GitLab an epic is no child, and an epic that depends on it is under what it blocks), its children (an epic's, or on GitHub any issue's sub-issues: the open ones a line each, the closed ones counted, `✓ 3 closed`), what blocks it outside its own children and what it blocks (its own epic left out), its due date, its milestone with the milestone's due date, labels, branch, tracked time, pull requests (MRs on GitLab) and commits that refer to it. Then its description, its first three lines until it is folded open (four lines or fewer show whole), and its comments, newest first: the newest unfolded, its first three lines and how many more, which show the rest when pressed, and each older one a line with its first words, which unfolds it. A section folds on its rule. What is unfolded holds over Refresh; an issue opened again starts folded. The detail scrolls between its top row and its bottom line, which stay put, and follows Tab to what is out of view. Its top row: `[ ← ]` (b), Prompt (p), which drafts a prompt from the issue (and assigns you first), and `[ ☰ ]`, the menu, with Assign Me or Unassign Me (a), Close or Reopen (c), Open in Browser (o) and Refresh (r); the hotkeys work with the menu shut. Every pane's top row ends in `[ ☰ ]`, with Refresh (r) and Help (h) in it. Help shows a page that says what each sign and colour means, the marks, the fold marks, the signs under an issue, counts and bars and the colours, each drawn as the panes draw it; it is the same page in every pane, it scrolls as a detail does, and `[ ← ]` returns to the list or detail it was opened over. Each issue under Epic, Children, Blocked by and Blocks is a line to select: it opens that issue's detail in the same pane, `[ ← ]` returns to the issue it was opened from, and from there to the list. Each of these has its mark before its number, as in the lists, and no state word: an open blocker that is itself blocked is ⊘, which costs a request per open blocker on Forgejo and GitLab (GitHub says so with the blocker); what the issue blocks waits on it, so it is ⊘ (● when yours) while the issue is open, and is asked as a blocker is once the issue is closed; an epic's own children never count as its blockers; a closed one is a grey ✓. Pull requests have no mark: merged says so, and a closed one is a grey ✓. Issues in another repo are left out on every forge, since What's Next shows this repo's numbers only. Once one of these changes the issue (Open in Browser aside), the pane goes back to the list the issue was opened from, What's next or Epics, which shows the change; a refused change keeps the issue open with why. Assigning and closing need a token with `write:issue` and push rights on the repo (on GitLab, `api` and Reporter or higher); setup's Actions step says whether What's Next may, and why not. After a change, What's next shows the issue as the change left it, read again from the forge, for 30 seconds, since a forge's lists may lag a change (GitHub's do, by a few seconds). When the repo has open epics, an Epics pane opens as a tab next to What's next (Refresh opens it once the first epic is there, and closes it when none is left): the epics of one open milestone, at first the one due first, each with a bar of its closed children (the milestone filter switches to another milestone, to the epics without one, or to All, a group per milestone); under it the line any issue row has (how many open issues block it outside its own children, its due date, its labels, the Epic label too, and its age), and, folded, a line with what there is for you among its children, each mark with its count in the order the rows are listed (children ● 2 · ○ 2 · ◌ 3 · ⊘ 1), or children all closed (amber: close it) once every child is; its ⊕ or ⊖ folds it open on its open children, as rows like What's next's (● yours, ⊘ blocked, ◌ with others, their name at the right, ○ available), and the rest of its row opens the epic's detail. The epics form a tree: a child with children of its own has a ⊕ or ⊖ in place of its mark, coloured by how it stands for you (green yours, dim blocked, plain otherwise, with others named at the right), with closed/total of its children at the right, and folds open on them two columns further in, as deep as the forge goes. On GitHub that is any sub-issue with sub-issues of its own, label or not, its count coming with it. On Forgejo an epic another epic depends on is no child of it but something it waits for, and on GitLab a related link does not say which issue is the parent, so there the tree is one level deep. An epic held by an open epic in the milestone filter shows only under it, not also at the top; an issue shown a second time (under two parents, or in a loop) shows ↑ and shown above, and does not fold. Children are asked when their parent first folds open; what is folded open holds over Refresh and Back. When the repo has open milestones, a Milestones pane opens as a tab after Epics, the same way (`/next` opens it again after it was closed): every open milestone, the one due first at the top and those without a due date last, each with a bar of its closed issues and closed/total, and under it one line, as under a folded epic: its due date, coloured as elsewhere, then what there is for you as far as the pane already knows without asking (yours from the lists; available, with others and blocked only once every issue in it that is not yours has been checked for blockers), or all closed (amber) once every one is; how many are open is read from closed/total, and what it does not know shows nothing. It has no milestone filter. Its ⊕ or ⊖ folds a milestone open on its open issues, taken from the lists already loaded, as rows like an epic's children (● yours, ⊘ blocked, ◌ with others, their name at the right, ○ available), then how many are closed; each one not yours is checked for blockers once, as What's next checks its own, and the line under the milestone then says all there is for you. Its epics come first, each with a bar of its closed children and under it the same two lines as on the Epics pane; its ⊕ or ⊖ folds it open on its tree, as on Epics, and what is folded open is shared with Epics. An issue an open epic in the milestone holds shows only under that epic, not also in the list, and an epic held by another epic in it only under that one. An epic's own children never count as its blockers, and they are asked once for Milestones and Epics both. What there is for you under the milestone leaves its epics out. A row opens the issue's detail, and Back returns to Milestones. The rest of a milestone's row, open or closed, opens its detail, which reads as the issue detail: the title, once closed with a grey ✓ before it and under it how long ago it closed (GitLab does not say when), its due date under Due, the bar with closed/total and how many are open, or all closed (amber while the milestone is open), what there is for you (its issues are asked when the detail opens, unless a fold already did, and the two share them), then two sections that fold on their rule: Issues, its issues as the same tree as in the list, open at first, and Description, its first three lines and how many more until it is folded open (a description of four lines or fewer has nothing to fold). Each milestone opens so; Refresh keeps what is unfolded. Its menu holds Open in Browser for the milestone's page on the forge, Close or Reopen, and Refresh. Back returns to the list with its folds as they were. Close and Reopen act at once, as on an issue, open issues and all (they keep the milestone); the pane then goes back to the list, read again, where a closed milestone sits under Closed, and a refusal keeps the detail open with why. They need the same token rights as closing an issue; on GitLab a milestone of a parent group closes in that group, so the token must be allowed to change the group. A folded milestone asks the forge nothing; folds hold over Refresh, which checks again only the milestones folded open. Under the open milestones, a Closed rule, folded at first, holds the last three milestones closed, newest first (on GitLab, which does not say when a milestone closed, the last changed), each a grey row ending in ✓; folded open, a closed milestone shows its open epics and issues as above, its closed epics as grey rows ending in ✓, and how many of its issues are closed. An epic is an issue with the Epic label; its children are the issues it depends on (on GitLab, the issues it links as related; on GitHub, its sub-issues). The milestone filter switches from what was loaded, and an issue opened again shows from memory; Refresh and `/next` ask the forge again. `/next` opens the panes with What's next in front and gives it the keyboard: the arrow keys and hotkeys work at once, and Esc returns to the prompt. A pane that opens later, on a reload, comes in front of the rest. `/next epics` (or `e`) opens the panes with Epics in front, the same way; `/next next` (or `n`) does what `/next` does. `/next help` opens What's next on the help page. When another plugin, a user command or an MCP server already has `/next`, the command is `/whats-next` in that session, and a toast says so. | a Forgejo, GitLab or GitHub access token; Forgejo, Gitea, GitLab or GitHub |

What's Next has eight settings. **Compact** (`ask`, `on` or `off`): lists without an empty line between rows; with `ask`, What's Next asks once, after Icons. **Epic label** (default `epic`): the label that makes an issue an epic; on GitLab its children are the issues it links as related, on GitHub its sub-issues. **Debug** (off by default): a line under the bottom line counts What's Next's requests to the forge, for the last action and for the session (`↯ Refresh: 6 requests · 41 this session`). **Icons** (`ask`, `icons` or `text`, in `/config` under What's Next): buttons as Nerd Font
icons or as words; with `ask`, What's Next asks once, right after setup. **Forgejo tokens**: Forgejo or Gitea
access tokens, kept in secure storage. A bare token is for every host; more hosts take `host=token`
pairs separated by spaces (`git.example.org=<token> codeberg.org=<token>`), and a pair wins over a
bare token. `/config` does not list it: set it with `/plugin configure whats-next@egribnau-mods` (setup names the marketplace What's Next was installed from). A token needs `write:issue`,
`read:repository` and `read:user` (to know which issues are yours); with `read:issue` in place of
`write:issue`, What's Next is read only and cannot assign or close. **GitLab.com token**: a gitlab.com access token, kept in secure storage.
**Private GitLab token**: an access token for your own GitLab, any host but gitlab.com, kept in secure
storage; `host=token` pairs separated by spaces still work for more than one host. A `gitlab.com=<token>`
pair there still counts for gitlab.com when GitLab.com token is empty. A GitLab token needs `api` to
assign and close, or `read_api` to read only. **GitHub token**: a GitHub access token, kept in secure storage, for
github.com and GitHub Enterprise; `host=token` pairs separated by spaces for more than one host. A fine-grained
token needs the Issues permission (read and write to assign and close, read to read only), a classic one `repo`.
What's Next reads no environment variables and no other tool's files. A token goes only to the host it is
for, as the forge setup found there, and What's Next shows it nowhere: a forge's error that echoes it back
shows `<token>` in its place.

What's Next is for the terminal. A Code session in the Claude desktop app loads it but gets none of its
settings: the secret token settings stay empty there, so the pane stops at the Token step. The desktop app
also runs the copy `claude plugin update whats-next@egribnau-mods` made from the last commit, not the
working folder.

To edit What's Next and see each change without a push, add this working copy as a marketplace
(`claude plugin marketplace add ~/dev/personal/claude-mods`) and install from it; Claude Code then
reads the folder itself, and `/reload-plugins` picks up an edit.
